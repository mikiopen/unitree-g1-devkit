# 反馈、部署与故障恢复

类型：扩展设计指南。提供接口与验证方向，具体实现由使用者完成。

## 能力目标

让开发者知道任务和设备当前状态，并能复现启动、定位故障、恢复运行和回退部署。先做单设备、单任务的完整记录，再扩展监控平台与多机管理。

## 前置条件

每个模块有健康状态定义、输入输出、依赖、配置与启动/结束方式。明确谁管理进程，谁确认设备状态，哪些恢复操作会产生实际动作。

## 输入输出与接口

| 信息 | 记录内容 | 解释边界 |
| --- | --- | --- |
| 健康 | 进程、依赖、设备连接、数据新鲜度 | 进程活着不代表功能可用 |
| 任务 | 关联ID、目标、阶段、错误、实际结果 | 通信成功不代表业务成功 |
| 性能 | 采集、处理、排队与响应耗时、丢失情况 | 先定义时钟与统计窗口 |
| 部署 | 软件/配置/资源标识、目标环境 | 镜像一致不代表固件兼容 |
| 恢复 | 故障、处理、设备状态、是否允许继续 | 自动重启不等于恢复控制权 |

状态界面至少区分有效、过期、未知、失败与恢复中。告警应有产生条件、清除条件和处理入口，避免每条日志都成为告警。

## 最小示例

1. 按[07掉线诊断](../tutorials/07-fleet.md)生成正常、失联和恢复记录，说明每种结果能确认什么。
2. 按[12界面](../tutorials/12-ui.md)显示状态，不把未知结果渲染成成功。
3. 写启动依赖图：配置/资源检查 → 接入 → 状态就绪 → 任务服务 → 界面；停止时明确如何终止任务、确认设备结束并释放资源。
4. 写一份回退演练表，记录旧配置、资源兼容性、停止条件、恢复后的只读检查；仅做设计时注明未实机演练。

## 可修改与扩展点

可增加systemd/容器部署、日志聚合、指标面板、权限、OTA与回滚。重连或重启后的任务默认如何处理需要明确：查询设备状态、对账未完成任务，再决定取消、恢复或人工处理。

升级前固定代码与资源标识，确认目标设备和兼容性；失败回退还需考虑配置格式、模型和数据变化。敏感配置按部署环境注入，公开文档只保留字段与占位。

## 验证方法

| 检查项 | 预期结果 | 提交证据 |
| --- | --- | --- |
| 可观测 | 从一次任务定位到设备与模块日志 | 关联记录 |
| 启停 | 依赖顺序与设备结束状态明确 | 启停清单 |
| 恢复 | 断线/重启不造成未知任务重复执行 | 恢复事件线 |
| 回退 | 回退后接口、配置与资源仍兼容 | 演练结果或明确待验证项 |

本仓库[预检](../preflight.md)与自动测试不会替使用者部署服务或发布OTA。
