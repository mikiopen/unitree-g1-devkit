# 从场景需求拆解六环节

类型：扩展设计指南。提供接口与验证方向，具体实现由使用者完成。

## 能力目标

把场景描述变成可分工、可替换、可验收的能力清单。先明确成功条件，再决定要哪些算法与设备；每个场景都走完整六环节。

## 前置条件

理解[完整框架](../learning-framework.md)与[模块接口](interfaces.md)。区分场景设计、已有最小示例、参考源码和自己需要实现的部分。

## 输入输出与接口

| 环节 | 语音查询状态 | 自主巡检 | 拿取并递送物体 |
| --- | --- | --- | --- |
| 设备接入 | 音频输入与状态接口 | 移动、传感器、检查设备 | 相机、移动、手臂与手部 |
| 感知 | 语音转文字 | 定位、障碍与检查观测 | 目标、抓取位姿、交付目标 |
| 决策 | 意图校验与目标选择 | 路线、到点作业、异常分支 | 导航、接近、抓取与交付顺序 |
| 执行 | 查询；需要时播放答复 | 行走与检查动作 | 移动、抓取、持有与释放 |
| 反馈 | 状态来源与查询结果 | 位置、进度与检查证据 | 持物、动作与交付确认 |
| 部署维护 | 模型/配置与日志 | 地图/路线、服务与恢复 | 标定/资源、任务记录与恢复 |

语音查询可借现有文件ASR、白名单与模拟状态做小闭环。巡检和拿取递送仅提供拆解方向，不是仓库已有完整应用。

## 最小示例

1. 选择一列，将“成功”改写成可观察条件。例如查询成功要求状态有效且来源明确；巡检成功要求指定检查项都有结果。
2. 为每一环节填写输入、输出、负责人模块与缺失条件。
3. 先用固定输入或模拟技能串流程，再逐个替换成真实模块，每次只改变一个关键条件。
4. 为每个关键失败点写任务去向；设备适配前先完成纸面或模拟评审。

### 三个场景的失败练习

- 查询：识别错字、未知请求、状态过期、播放失败。状态查询成功和语音播放成功分别记录。
- 巡检：定位丢失、通道封闭、检查传感器失败、单点未完成。部分完成不能冒充整条路线完成。
- 递送：目标不存在、位姿不可靠、抓空、途中持物丢失、无人接收。释放物体不自动等于完成交付。

## 可修改与扩展点

将语音换成界面按钮，将检测器换成其他模型，或把任务从单机扩展成多机时，优先保持任务结果与接口语义一致。

选技术路线时按缺口查[感知](perception.md)、[导航](navigation.md)、[任务](tasks.md)、[操作](motion.md)、[仿真数据](simulation-data.md)与[运行维护](operations.md)，不要为了覆盖目录而引入不需要的组件。

## 验证方法

| 检查项 | 预期结果 | 提交证据 |
| --- | --- | --- |
| 需求 | 成功、部分完成与失败有明确区分 | 场景验收单 |
| 分工 | 每个输入输出都有负责模块 | 六环节能力表 |
| 最小闭环 | 固定输入可走完任务并产生反馈 | 模拟/设计记录 |
| 扩展 | 替换模块后继续符合接口与验收项 | 替换前后对照 |
| 集成 | 各子模块通过后再声明整场景范围 | 集成记录及限制 |

交付建议使用[作品模板](../portfolio-template.md)，只声明已有证据支持的能力。
