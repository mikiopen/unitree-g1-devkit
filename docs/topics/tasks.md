# 技能接口与任务编排

类型：扩展设计指南。提供接口与验证方向，具体实现由使用者完成。

## 能力目标

把“查询、导航、播放、抓取”等能力包装成技能，再组成可追踪的任务。让任务层决定何时调用，技能层负责完成约定操作并反馈结果。

## 前置条件

先完成[04命令生命周期](../tutorials/04-control.md)与[10白名单](../tutorials/10-router.md)。任务设计至少需要设备能力清单、当前状态与技能的失败/取消语义。

## 输入输出与接口

| 技能契约 | 内容 |
| --- | --- |
| 参数 | 目标、单位、可选项、允许范围 |
| 前置条件 | 状态是否有效、设备是否支持、是否持有控制权 |
| 成功条件 | 用哪个实际反馈判定，而非仅收到调用返回 |
| 异常与取消 | 可否取消、如何确认结束、错误是否允许恢复 |
| 资源 | 占用的执行器、音频、相机或其他排他资源 |
| 副作用 | 重复请求、超时重试是否会重复动作 |

### 建议任务状态

`待检查 → 已接受 → 执行中 → 成功 / 失败`；取消分为“取消请求中”和“已确认取消”。前置检查可直接拒绝。超时可进入“结果未知/待确认”，查明设备端状态后才能决定下一步。

这些是设计建议，并非现有白名单已实现的任务引擎。状态机适合先把有限流程讲清；任务变复杂后可按需求选择行为树或其他编排方式。

## 最小示例

1. 设计两个模拟技能：读取状态、显示结果。每个填写参数、前置条件、成功证据与错误。
2. 将两者串成“读取成功才显示有效结果”；失败时显示未知，不沿用旧值冒充成功。
3. 模拟执行中取消、回复迟到与重复请求，写出每一步的任务状态。
4. 用现有白名单输出作为入口样本；后续自行实现技能调度，不把dry-run结果当执行记录。

可参考的任务事件字段：`task_id`、`device_id`、`skill`、`state`、`sequence`、`error`。序列号与会话标识的使用由项目定义。

## 可修改与扩展点

增加导航、抓取、播报、巡检技能时，先完善单技能契约，再组合。并发任务需要资源冲突规则，例如两个任务不能不经仲裁同时控制同一执行器。

接入大模型时，将其输出视为候选计划：校验技能白名单、参数结构、目标权限与实时前提，再交给执行器。工具错误作为任务反馈，不能通过生成一段文字宣布动作成功。

## 验证方法

| 检查项 | 预期结果 | 提交证据 |
| --- | --- | --- |
| 成功链路 | 每一步都有实际结果支持 | 事件时间线 |
| 异常传播 | 子技能失败不会被外层标为成功 | 失败任务记录 |
| 取消与迟到 | 取消确认与迟到回复处理符合契约 | 两类时序记录 |
| 并发与重试 | 无资源冲突和不明原因重复执行 | 冲突/重复用例 |

任务结束时同时说明业务结果与设备状态；业务取消不保证设备已经停止。
