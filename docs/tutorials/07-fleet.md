# 第 07 章：多设备与掉线诊断

> 环节E · 反馈。本章成果：群发、单台、掉线与恢复四组记录。

## 能力目标

让两个模拟设备分别响应全部与单台查询，再验证一台掉线和恢复。

- 按目标收集多个设备的反馈。
- 解释缺失回复不一定等于断电。
- 区分同时发送与严格同步执行。

### 准备与配置

终端A/B/C都在仓库根目录。A使用19006、B使用19007，保留各接收端运行窗口。

## 输入输出与接口

all是客户端分别发送到已知endpoint，不是自动发现或局域网广播。每个endpoint只代表本次通信位置；真实系统还需设备身份、心跳期限、反馈与幂等设计。

| 边界 | 约定 |
| --- | --- |
| 输入 | 多端点、目标标识、命令与超时 |
| 输出 | 各端点回复、未匹配情况及恢复记录 |
| 错误边界 | 无回复不能直接推断设备断电 |

## 最小示例

1. 终端A启动g1-a，终端B启动g1-b，分别执行：

   ```text
   python examples/06-udp-demo/udp_demo.py serve --robot-id g1-a --port 19006
   python examples/06-udp-demo/udp_demo.py serve --robot-id g1-b --port 19007
   ```

2. 终端C查询全部：

   ```text
   python examples/06-udp-demo/udp_demo.py send --endpoint 127.0.0.1:19006 --endpoint 127.0.0.1:19007 --target all --command status
   ```

3. 只查询g1-a时只列其端点：

   ```text
   python examples/06-udp-demo/udp_demo.py send --endpoint 127.0.0.1:19006 --target g1-a --command status
   ```

4. 在B用Ctrl+C停止g1-b，再查all；记录19007缺失。重启B后再查all，应恢复两个回复。
5. 将target换成未知ID，解释无人回复的原因。最后用Ctrl+C结束A/B。

## 可修改与扩展点

增加设备状态面板或任务分配策略，区分命令筛选与在线诊断；当前实验没有实现导航调度或协同运动。

### 实践成果

设计在线、离线、未知三种显示状态，并写明何时过期。交付四组结果及状态规则。对应工作：多设备管理、分布式应用与集成排障。

## 验证方法

| 检查项 | 预期结果 | 提交证据 |
| --- | --- | --- |
| 全部与单台 | all返回g1-a/g1-b；单台返回g1-a | 两组结果 |
| 掉线与恢复 | 停B后仅A回复；重启后两端恢复 | 两组结果 |
| 沉默解释 | 目标过滤、丢包、超时、不可用都可能造成缺失 | 一段诊断说明 |

### 常见问题

| 现象 | 检查与处理 |
| --- | --- |
| 目标为A却报告B缺失 | 客户端会等待每个列出的端点；单台查询只列目标端点。 |
| 回复顺序变化 | 按robot_id集合比较，不依赖到达顺序。 |
| 同时发就算同步吗 | 分别测发送、接收、实际执行时刻；本例只证明路由与收集。 |
